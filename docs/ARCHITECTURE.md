# Architecture — Chinfon Kaizen 360° v3

```text
Browser (Win10 / mobile)
  -> Go net/http + html/template (embedded)
  -> database/sql
  -> SQLite WAL (data/kaizen.db)
  -> local attachment folder (data/uploads/)
```

## Runtime shape

- One binary. Templates, CSS, JS and SQL migrations are embedded.
- `SERVER` owns all authorization and valuation. The browser only renders and
  previews Net = A − B; the server recomputes at review time.
- SQLite `PRAGMA journal_mode=WAL`, `synchronous=NORMAL`, `foreign_keys=ON`,
  `busy_timeout=5000`, one connection. The one-connection rule is safe because
  every query closes its rows before the next query (regression test covers
  `masterUsers`).
- Uploaded files are not served by a static file server. A handler checks the
  record scope and emits `Content-Disposition: attachment`.

## Domain model

```text
initiative
  ├─ initiative_participant   (co-authors + share %)
  ├─ initiative_review        (one row per decision)
  ├─ initiative_history       (append-only stage/action log)
  ├─ initiative_attachment    (metadata + SHA-256)
  └─ audit_log                (cross-record security log)

master:
  md_department, md_employee, md_track, md_stage,
  md_implementation_status, md_document_type, md_reward_tier
settings:
  app_setting (demo_mode)
security:
  rbac_role, rbac_permission, rbac_role_permission,
  app_user (csrf_token, TOTP ciphertext, lock/backoff),
  app_user_role, app_session (mfa_passed)
```

The canonical identifier is `SI-YYYY-NNNNN`, generated by
`initiative_sequence`. It is immutable (DB trigger) and independent of
department codes.

## Authorization

Two layers, both mandatory:

1. **Visibility** (`VisibilityClause`, `CanView`): which rows may be read.
2. **Action** (`CanAct`, stage permission): which transition may be performed.

`ADMIN` is not a hard-coded bypass in the handlers: it has all permissions and
is normally created with `dept_scope=ALL`. Removing a permission in the RBAC
matrix takes effect immediately because permissions are loaded per request.

## Workflow transaction

`applyStageReview` does the following in one SQLite transaction:

1. optimistic lock on `(id, stage_code, record_status='OPEN')`;
2. update valuation (review stage) or approved override (approve stage);
3. insert `initiative_review`;
4. move stage or set `record_status=REJECTED`;
5. insert `initiative_history`.

If any step fails, nothing is committed. A second reviewer acting on stale data
gets a conflict instead of double approval.

## Money

All amounts are integer VND. The reward function is pure and tested against
policy boundaries. Annex 03 multiplies by 1.2 and caps at 100,000,000.
Non-financial Mục 5.2 is a separate table and never receives the 1.2x factor.

## MFA and sessions

- Every account must enrol TOTP after the password step. The TOTP secret is
  encrypted with AES-256-GCM using `data/mfa.key` or `APP_MFA_KEY`; only
  ciphertext is stored in SQLite.
- Password verification creates a **partial session** (`mfa_passed=0`, 10
  minutes) that can only reach `/mfa/setup`, `/mfa/verify`, `/mfa/qr.png` and
  logout. Successful TOTP verification extends it to a 12-hour full session.
- Codes are one-use: `last_totp_counter` rejects replay. Validation allows a
  ±1 step window for clock drift.
- Per-account backoff after 5 failures: 1, 2, 4, 8, up to 15 minutes. A
  successful MFA resets it.
- Admin reset (not self) and the `reset-mfa` CLI clear TOTP state and sessions.
  HSTS is enabled when `COOKIE_SECURE=true`. Passkeys/WebAuthn are not included.

## Staff onboarding and demo mode

- `md_employee` now carries `email`, `mobile_num`, `report_to`, `position_title`
  (CSV `job_title`) and `work_group` (CSV `group`).
- CSV import upserts departments, employees, accounts and roles in one SQLite
  transaction. Valid rows are committed; row-level errors are skipped and
  reported. File/header errors block the import.
- New accounts store `password_hash='pending'`. First login compares the entered
  PIN with the last five digits of `mobile_num`, then `withUser` forces a password
  change. The PIN is never stored and no PBKDF2 work is done during import.
- `app_setting.demo_mode` controls whether `initiative.is_demo=1` rows are
  visible. Migration 007 sets it to `0`; production does not seed demo data.
  Existing demo rows stay archived/hidden. `VisibilityClause` and `CanView`
  enforce the filter.
- CSV rows without `mobile_num` are imported as personnel only; the account is
  skipped until a later import supplies the mobile. The admin UI and the
  `import-staff` CLI (defaults to `data/uploads`) use the same parser/apply path.
- `role=council` in the CSV or the council-provisioning form creates a COUNCIL
  account with `dept_scope=ALL`; existing passwords are not reset by that form.

## Deliberate limits

- Single-node SQLite; no horizontal scale.
- No email/push notification; SLA overdue is dashboard-only.
- No e-signature; print sheet has signature blocks.
- No HR system sync; master data is maintained by CSV import or admin screens.
- CSV (UTF-8) is the staff import/export format; native XLSX is not parsed.
- HRD CSV is the payroll integration boundary.
